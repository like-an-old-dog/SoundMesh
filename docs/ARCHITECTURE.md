## 1. 拓扑

没有服务器，没有中继，也没有信令。每一对「发送端 → 接收端」都是一条独立的 TCP 连接，接收端可以同时挂多条；发送端也可以同时服务多个接收端（各自一条连接、各自一个队列）。

```
发送端 A ──┐
发送端 B ──┼──► 接收端（MixBus）──► 系统输出
发送端 C ──┘
```

一台设备可以同时是发送端和接收端（双向模式），但**同一次安装同一时间只运行一种模式**。这是为了避免采集环回和端口冲突，也让"谁是接收端"这件事在界面上始终明确。

## 2. 发现（UDP 49633）

| 方向 | 载荷 |
| --- | --- |
| 接收端 → 广播 | ASCII `SOUNDMESH FIND 2` |
| 发送端 → 应答 | UTF-8 `SM2\|<设备ID>\|<设备名>` |

- 设备 ID 是 32 位十六进制字符串（GUID `N` 格式），首次运行生成并持久化。
- 设备名取主机名，`|` 会被替换成空格，避免破坏分隔。
- 接收端向**所有**候选广播地址各发一份：每个网卡按子网掩码计算定向广播，再补一个 `255.255.255.255`，然后收 1200 ms。
- 发送端对收到的查询**原路应答**（回给 `RemoteEndPoint`），不广播自己的存在——只有主动扫描才会出现，减少无关流量。
- 列表里的地址取自**应答报文的源地址**，不是报文内容。这样多网卡电脑会把正确的那块网卡的地址暴露出来。
- 网卡选择有打分：有默认网关 +10，Wi-Fi +5，命中 `vmware|virtual|hyper-v|wsl|vpn|tunnel|vethernet|tap-|tun` 等描述 -30，`169.254.x.x` 直接跳过。二维码与网页桥接优先用分数最高的网卡。

> 报文里没有版本号以外的协商能力，因此发现是"尽力而为"的：同网段的设备才可见。

## 3. 音频连接（TCP 49632）

连接后双方各说一行 ASCII（`\n` 结尾，单行上限 80 字节，超长判为协议错误）：

```
接收端 → 发送端:  SOUNDMESH2 <8位配对码>[ <8位反向配对码>]
发送端 → 接收端:  OK 48000 2            // 成功
                  ERR                    // 配对码错误
```

- 反向配对码只在双向连接的第一个握手出现；发送端验证通过后回调 `ReverseRequested(ip, pin)`，由上层发起反向连接。
- 另有控制帧 `SM2-FOCUS <配对码>` → `OK FOCUS`，用于「把监听切到本机」让对端暂停监听。
- **超时**：连接 6 s，握手 5 s，单帧读取 15 s。任何一次超时都视为断流。
- **重连**：指数退避 1 → 2 → 4 → 8 s（上限 8 s），保留音量与静音状态；收到 `OK` 后立即把退避重置为 1 s。
- **配对码错误**会被当作认证失败计数：同一 IP 每分钟最多 6 次未通过尝试，超过后直接断开。成功连接不计入。
- 配对码一次性校验通过即可，之后同一连接不再校验——所以要防止中间人，只能靠网络本身可信。

### 多接收端

发送端为每个订阅者维护一个有界队列（容量 8 帧，`DropOldest`）。网络慢的接收端只会丢自己的旧帧，不会拖慢采集时钟，也不会影响其他接收端。

## 4. 音频帧与缓冲

| 项目 | 值 |
| --- | --- |
| 采样率 | 48 000 Hz |
| 位深 / 声道 | 16 bit / 2（交织，小端有符号） |
| 帧长 | 1920 字节 = 480 帧 = **10 ms** |
| 帧边界 | 固定长度，无长度前缀、无压缩 |

**没有封装、没有序号、没有时间戳。** 连接本身是可靠有序的，接收端只按固定长度切帧。丢包/超时表现为整体断流并重连，而不是单帧丢失——这是"局域网 + TCP"前提下的简化取舍。

### 自适应环形缓冲（`AudioRing`）

- 环形缓冲容量 48 000 个 float（1 s）。
- 起始缓冲 = 档位值（25 / 70 / 90 ms）。攒够 `TargetMs` 才开始出声，避免一上来就欠载。
- `TargetMs = min(160, 起始值 + 恢复量)`。每次欠载把恢复量 +25 ms，连续稳定 30 s 后再每次 -5 ms 回落。
- 积压超过 200 ms 时，直接丢弃到 `max(80 ms, 起始值)`，**宁可跳一小段也不让延迟累积**。
- 欠载时输出静音（`Array.Clear`），并把状态置回"未就绪"，让下一轮重新预缓冲。

结果就是：延迟随网络状况自适应，但有硬上限 160 ms；短暂抖动换来一次轻微断音，而不是越来越高的延迟。

## 5. 混音

每路：`样本 × 每路增益（默认 0.65，静音为 0）`，累加到总和；再 `× 总音量（默认 0.8）`。
最后过一个软的峰值限制器：目标是峰值 `0.95`，**压制立即生效、恢复缓慢**（Windows 每缓冲 +0.01，Android +0.005），避免增益在峰值附近抖动造成"抽气"感。

- 累加用 float，不削波；限制器保证输出不越界。
- 66 路同时混音在测试中仍落在输出范围内。
- 逐路电平表用 `level = max(peak, level × 0.8)` 做衰减，供界面显示。
- 输出侧 Windows 用 `WaveOutEvent`（45 ms 缓冲 × 3），Android 用 `AudioTrack`。

## 6. 采集路径

### 6.1 Windows

| 模式 | 实现 |
| --- | --- |
| 普通共享 | NAudio `WasapiLoopbackCapture` 抓默认播放设备的回环，重采样到 48 kHz，转 16 bit 立体声 |
| 进程排除（双向 / 静音本机） | 独立进程 `SoundMeshCapture.exe`，用 `ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK)` + `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` 排除声汇自身进程树，PCM 从 stdout 管道回主程序 |

- 进程回环需要 Windows build 20348+；失败时界面会提示改用普通模式。
- 原生 helper 的 `WAVEFORMATEX` 固定为 48 kHz / 16 bit / 2ch，`AUDCLNT_STREAMFLAGS_LOOPBACK | AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`，静音包会被填零。
- 「共享时静音电脑当前输出」= 临时把当时的默认播放设备静音，退出时恢复原状态；异常退出不会恢复。
- 单声道源会复制到两个声道（`StereoSource`），不做假立体声处理。

### 6.2 Android

- `MediaProjection` + `AudioPlaybackCaptureConfiguration`，只捕获**媒体**类型的音频，并对声汇自身的 UID 做排除。
- 采集跑在 `foregroundServiceType="mediaProjection|mediaPlayback"` 的前台服务里，持有 Wi-Fi 高性能锁与 `PARTIAL_WAKE_LOCK`。
- 受保护内容与通话声音受系统限制，无法采集。

### 6.3 发送节拍

发送端不依赖采集回调触发网络写入，而是用 `Stopwatch` 驱动一个 10 ms 的时钟（`next += 10`）。采集缓冲低于 10 ms 时发静音帧占位，超过 35 ms 才认为已 pre-roll。这样网络侧的帧间隔严格 10 ms，接收端的缓冲模型才能成立。

## 7. 双向空间

```
A ──SOUNDMESH2 <A的pin> <B的pin>──► B      （A 作为发送端连 B）
B ──SOUNDMESH2 <A的pin>──────────► A      （B 作为发送端连 A，用 A 的 pin 认证）
```

1. A 侧发起连接，握手第二行带上自己的配对码作为反向码。
2. B 验证 `A的pin` 通过后，用 `A的反向码` 主动连回 A。
3. 两端各自把对方当作一路来源混音，同时继续采集自己的声音。

「把监听切到本机」= 本机打开监听 + 向所有已连接对端发 `SM2-FOCUS <pin>`，对端收到后暂停输出。这样同一份声音不会在两副耳机里重复。

三台设备不做全网状自动发现，需要**逐对连接**（A–B、A–C、B–C）。每台的混音只包含自己直连的对端。

## 8. iPhone 网页桥接（TCP 49634）

Windows 端内置一个最小 Kestrel 应用：

| 路由 | 说明 |
| --- | --- |
| `GET /` | 内嵌的 `index.html`（作为程序集资源嵌入，不是磁盘文件） |
| `GET /styles.css` `/app.js` `/audio.js` | 静态资源 |
| `GET /api/sources` | 当前可混音的来源列表（需 Bearer 令牌） |
| `GET /api/discover` | 在电脑侧做一次局域网发现（需 Bearer 令牌） |
| `POST /api/sources` | 添加一台设备：校验 IPv4 + 8 位数字配对码，并**先真实连一次**确认可用（需 Bearer 令牌） |
| `WS /api/audio` | PCM 推送（需 Bearer 令牌） |

- 令牌是 24 字节随机数的十六进制串（48 字符），每次启动重新生成，只出现在二维码 URL 的 `#fragment` 里，因此不会进入请求行或访问日志。
- 校验用 `CryptographicOperations.FixedTimeEquals` 做定长比较。
- `/api/sources` 只接受**同链路**的 IPv4 地址（`OnLink` 检查），拒绝公网与其他网段地址；请求体上限 2048 字节。
- 响应头固定 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`。
- 网页端用 `AudioContext` + `AudioWorklet`/缓冲区队列播放，逐路增益与静音在浏览器内完成。

浏览器侧限制：局域网 HTTP（非安全上下文）下部分能力受限，Safari 的后台音频策略也可能挂起播放。**真机 iPhone 上的播放行为尚未验证**。

## 9. 线程与实时性

- 网络接收（`Tasks`）只负责把字节推进 `AudioRing`，加锁范围仅覆盖环形缓冲的拷贝。
- 播放回调（`WaveOutEvent` / `AudioTrack`）在 `Read()` 里做混音，用 `lock(sources)` 保护来源列表——不分配、不做 I/O、不建任务。
- 发送侧所有网络写入都是异步，订阅者队列满时丢最旧帧而不是阻塞。
- 接收与发送的异常都被限制在单个连接内，一条连接挂掉不影响其他通道。

## 10. 安全模型

| 项 | 现状 |
| --- | --- |
| 传输加密 | ❌ 明文 TCP / UDP |
| 身份认证 | 8 位数字配对码（发送端生成，约 26.6 bit 熵） |
| 暴力破解防护 | 每 IP 每分钟 6 次失败上限 |
| 发现报文 | 明文，含设备 ID 与主机名 |
| 网页桥接 | 每次启动的 48 字符随机令牌 + 同链路校验 |
| 依赖外部服务 | 无 |

**结论**：这是一个可信局域网内的工具。不要在公共 Wi-Fi、访客网络或任何可能被嗅探/中间人的链路上使用。加密链路在路线图上，但目前没有实现。
