## 1. 拓扑与融合会话

没有服务器，没有中继，也没有信令。每一对「设备 → 设备」都是一条独立的 TCP 连接，可以同时双向使用。

从 1.1 起每台设备只有一种会话：**「开始融合」= 同时采集并发送本机声音 + 同时接收并对端声音**。同一次安装在同一个时刻只运行一个会话，避免采集环回与端口冲突，也让"谁在监听"在界面上始终明确。

```
设备 A ──┐
设备 B ──┼──► 各自的 MixBus ──► 各自的输出
设备 C ──┘
```

一次配对会建立**两条方向相反**的连接（见第 3 节的反向配对码），所以三台设备只需逐对连一次：A–B、A–C、B–C。每台设备的混音只包含它直连的对端，不做全网状广播。

## 2. 发现（UDP 49633）

| 方向 | 载荷 |
| --- | --- |
| 发起方 → 广播 | ASCII `SOUNDMESH FIND 2` |
| 应答方 → 原地址 | UTF-8 `SM2\|<设备ID>\|<设备名>` |

- 设备 ID 是 32 位十六进制字符串（GUID `N` 格式），首次运行生成并持久化。
- 设备名取主机名，`|` 会被替换成空格，避免破坏分隔。
- 发起方向**所有**候选广播地址各发一份：每个网卡按子网掩码计算定向广播，再补一个 `255.255.255.255`，然后收 1200 ms。
- 应答方对查询**原路应答**，不主动广播，减少无关流量。
- 列表里的地址取自**应答报文的源地址**，不是报文内容——多网卡电脑因此能暴露正确网卡的地址。
- 网卡选择有打分：有默认网关 +10，Wi-Fi +5，命中 `vmware|virtual|hyper-v|wsl|vpn|tunnel|vethernet|tap-|tun` 等描述 -30，`169.254.x.x` 直接跳过。二维码与网页桥接优先用分数最高的网卡。

## 3. 音频连接（TCP 49632）

连接后双方各说一行 ASCII（`\n` 结尾，单行上限 80 字节，超长判为协议错误）：

```
发起方 → 对端:  SOUNDMESH3 <8位配对码>[ <8位反向配对码>]   // 1.2 时间戳协议
对端 → 发起方:  OK TIME3
发起方 → 对端:  PING  ×5            // 每次对端回一行自己的单调微秒时刻
对端 → 发起方:  <nowUs> ×5

发起方 → 对端:  CLOCK               // 之后每分钟一次的短连接复测
对端 → 发起方:  （5 次 PING/nowUs 应答）

// 旧客户端 / iPhone 网页：
发起方 → 对端:  SOUNDMESH2 <8位配对码>[ <8位反向配对码>]
对端 → 发起方:  OK 48000 2             // 成功，之后为 1920 字节纯 PCM 帧
                ERR                     // 配对码错误
```

- 反向配对码在同一个握手行里：对端验证通过后回调 `ReverseRequested(ip, pin)`，由上层发起反向连接。一次配对因此同时覆盖收发两个方向。
- 校时取 5 次往返中 **RTT 最短**的一次估算偏移（`offset = start + rtt/2 - remote`），因为最短 RTT 最接近对称路径；之后每分钟复测一次。
- 没有 `SOUNDMESH3` 支持的对端会返回 `ERR` 或直接断开，客户端捕获后改用 `SOUNDMESH2` 重连，进入独立缓冲模式。
- 另有控制帧 `SM2-FOCUS <配对码>` → `OK FOCUS`，用于「把监听切到本机」（第 7 节）。
- **超时**：连接 6 s，握手 5 s，单帧读取 15 s。任何一次超时都视为断流。
- **重连**：指数退避 1 → 2 → 4 → 8 s（上限 8 s），保留音量与静音状态；收到 `OK` 后立即把退避重置为 1 s。
- **配对码错误**会被当作认证失败计数：同一 IP 每分钟最多 6 次未通过尝试，超过后直接断开。成功连接不计入。
- 配对码一次性校验通过后，同一连接不再校验——所以只能靠网络本身可信来防中间人。

### 多接收端

发送端为每个订阅者维护一个有界队列（容量 8 帧，`DropOldest`）。网络慢的接收端只丢自己的旧帧，不拖慢采集时钟，也不影响其他接收端。

## 4. 音频帧与缓冲

| 项目 | 值 |
| --- | --- |
| 采样率 | 48 000 Hz |
| 位深 / 声道 | 16 bit / 2（交织，小端有符号） |
| 帧长 | 1920 字节 = 480 帧 = **10 ms** |
| 帧边界 | 固定长度，无长度前缀、无压缩 |
| 时间戳协议帧 | 1928 字节 = 8 字节大端微秒时间戳 + 1920 字节 PCM |

**旧协议没有封装、没有序号、没有时间戳**：连接本身是可靠有序的，接收端只按固定长度切帧，丢包/超时表现为整体断流并重连。1.2 的时间戳协议在每帧前加 8 字节采集时刻，用于跨设备对齐而不是用于重传——迟到超过播放期限的片段按缺音丢弃。

### 自适应环形缓冲（`AudioRing`）

- 环形缓冲容量 48 000 个 float（1 s）。
- 起始缓冲 = 档位值（25 / 70 / 90 ms）。攒够 `TargetMs` 才开始出声，避免一上来就欠载。
- `TargetMs = min(160, 起始值 + 恢复量)`。每次欠载把恢复量 +25 ms，连续稳定 30 s 后每次 -5 ms 回落。
- 积压超过 200 ms 时直接丢弃到 `max(80 ms, 起始值)`，**宁可跳一小段也不让延迟累积**。
- 欠载时输出静音，并把状态置回"未就绪"，让下一轮重新预缓冲。

## 4.5 时钟同步与播放时间轴

两端都支持时间戳协议时，接收端不再各自缓冲，而是把所有远端通道放到**同一条播放时间轴**上。

**发送端**（`FrameClock`）：以 10 ms 为步长给每帧分配采集时刻。相邻块的估计长度会因采样时钟差异抖动，因此把误差夹在 ±100 采样（约 2 ms）内；一旦跳变超过 50 ms，就判定为真实断点并重新对齐，而不是把断点抹平。

**接收端**（`Timeline` + `PlayoutClock`）：

- `PlayoutClock` 用 `(now - delay) × 48 / 1000` 算出当前应当播放到的采样序号，`delay` 即界面上的同步缓冲（100 / 150 / 200 ms，默认 150）。漂移超过 100 ms 直接重锚，超过 20 ms 则每次微调 1 个采样。
- `Timeline` 是 2 秒的环形表，按采样序号记录标签与浮点样本。写入时若相邻帧长度落在 400–560 采样之间，按线性插值重新采样到该长度；差值更大视为断点，保留其原始位置。
- 读取时按时间轴逐采样取值：命中就输出，缺失就补零并记一次 `Gaps`；写入时若时间戳早于已消费位置则记 `Late` 并丢弃。
- 因此**单路迟到只丢它自己那一段，不会阻塞其他通道**，多路混音在时间上始终对齐。

同步路径只作用于参与声汇混音的远端音轨。本机其他应用由系统直接输出，旧版本设备与 iPhone 网页仍走独立缓冲。测试用 100 / 150 / 200 ms 三档、两路来源其中一路反复 80 ms 突发停顿，验证输出逐样本对齐。
## 5. 混音与四层增益

1.1 有四层可调增益，作用点各不相同：

| 层 | 位置 | 影响 |
| --- | --- | --- |
| 每台远端设备 | 接收端混音前 | 该来源在当前监听端的音量与静音 |
| 其他设备合计（`NetworkMixer.Master`） | 接收端混音后 | 所有远端通道的总音量 |
| 本机发送（`AudioSender.OutboundPercent`） | 发送端编码前 | 出站信号，所有接收方都会听到变化 |
| 本机应用（`LocalSessions`，仅 Windows） | 系统音量会话 | 按比例压低其他应用，跳过声汇自身会话 |

混音公式：每路 `样本 × 每路增益（默认 0.65，静音为 0）` 累加 → `× 总音量（默认 0.8）` → 峰值限制器（目标峰值 0.95，**压制立即生效、恢复缓慢**，Windows 每缓冲 +0.01，Android +0.005）。

- 累加用 float，不削波；限制器保证输出不越界。
- 发送侧增益在写出站帧之前作用，因此只改变别人听到的音量，不改变本地混音。
- `LocalSessions` 只在值仍等于上次应用值时恢复基准音量，期间用户手动改过的会话不会被覆盖；结束融合时整体恢复。它只作用于默认播放设备，并跳过声汇自己的 PID。
- 66 路同时混音在测试中仍落在输出范围内。

## 6. 采集路径

### 6.1 Windows

| 模式 | 实现 |
| --- | --- |
| 进程隔离（1.1 的默认路径） | 独立进程 `SoundMeshCapture.exe`，`ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK)` + `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`，PCM 从 stdout 管道回主程序 |

- 原生 helper 的 `WAVEFORMATEX` 固定为 48 kHz / 16 bit / 2ch，`AUDCLNT_STREAMFLAGS_LOOPBACK | AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`，静音包会被填零。
- 进程回环需要 Windows build 20348+；失败时启动会直接报错。
- 发送端不依赖采集回调触发网络写入，而用 `Stopwatch` 驱动 10 ms 时钟（
ext += 10`）；采集缓冲低于 10 ms 时发静音帧占位，超过 35 ms 才认为已 pre-roll。这样网络侧帧间隔严格 10 ms，接收端的缓冲模型才能成立。

### 6.2 Android

- `MediaProjection` + `AudioPlaybackCaptureConfiguration`，只捕获**媒体**类型的音频，并排除声汇自身的 UID。
- 采集跑在 `foregroundServiceType="mediaProjection|mediaPlayback"` 的前台服务里，持有 Wi-Fi 高性能锁与 `PARTIAL_WAKE_LOCK`。
- 受保护内容与通话声音受系统限制，无法采集。

## 7. 监听接管

耳机接在哪台，就由哪台输出混音。

1. 该设备点「把监听切到本机」：本机打开监测输出（`SetMonitoring(true)`），并向所有已连接对端发 `SM2-FOCUS <pin>`。
2. 对端收到后暂停本地输出，避免同一份声音在两副耳机里重复。
3. 切换是"单向指令"：对端只是暂停监听，连接和发送都不受影响，随时可以再切回来。

## 8. Android 音量面板与系统媒体卡片

- 融合会话公开一个 `MediaSession`，把**远端混音总音量**映射到媒体会话的音量（卡片显示的百分比与进度条）。
- 在系统媒体卡片上拖动进度条 → 通过媒体会话回调改混音增益；实测从 80 改到 37 能被正确上报。
- 轻点卡片打开 `VolumePanelActivity`（「声汇音量」），内部是 `VolumeRow` 列表：
  - 本机 · 发给其他设备 → `AudioService.setLocalPercent`（出站增益）
  - 本机 · 系统媒体输出 → 系统 `STREAM_MUSIC` 音量（音量固定的设备会禁用该行）
  - 远端混音总音量 → `AudioService.setVolume`（总增益）
  - 每个远端设备一行 → `Remote.gain`
- 面板每 350 ms 同步一次，会话结束自动关闭。部分厂商的紧凑卡片布局会隐藏进度条，需要展开卡片。

## 9. iPhone 网页桥接（TCP 49634）

Windows 端内置一个最小 Kestrel 应用：

| 路由 | 说明 |
| --- | --- |
| `GET /` | 内嵌的 `index.html`（作为程序集资源嵌入，不是磁盘文件） |
| `GET /styles.css` `/app.js` `/audio.js` | 静态资源 |
| `GET /api/sources` | 当前可混音的来源列表（需 Bearer 令牌） |
| `GET /api/discover` | 在电脑侧做一次局域网发现（需 Bearer 令牌） |
| `POST /api/sources` | 添加一台设备：校验 IPv4 + 8 位数字配对码，并**先真实连一次**确认可用（需 Bearer 令牌） |
| `WS /api/audio` | PCM 推送（需 Bearer 令牌） |

- 令牌是 24 字节随机数的十六进制串（48 字符），每次启动重新生成，只出现在二维码 URL 的 `#fragment` 里，不会进入请求行或访问日志。
- 校验用 `CryptographicOperations.FixedTimeEquals` 做定长比较。
- `/api/sources` 只接受**同链路**的 IPv4 地址（`OnLink` 检查），拒绝公网与其他网段；请求体上限 2048 字节。
- 响应头固定 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`。
- 网页端用 Web Audio 播放，逐路增益与静音在浏览器内完成。

浏览器侧限制：局域网 HTTP（非安全上下文）下部分能力受限，Safari 的后台音频策略也可能挂起播放。真机尚未验证。

## 10. 线程与实时性

- 网络接收（`Tasks`）只负责把字节推进 `AudioRing`，加锁范围仅覆盖环形缓冲的拷贝。
- 播放回调（`WaveOutEvent` / `AudioTrack`）在 `Read()` 里做混音，用 `lock(sources)` 保护来源列表——不分配、不做 I/O、不建任务。
- 发送侧所有网络写入都是异步，订阅者队列满时丢最旧帧而不是阻塞。
- 接收与发送的异常都被限制在单个连接内，一条连接挂掉不影响其他通道。
- `LocalSessions` 与系统音量会话的枚举放在 UI 定时器里，遇到会话消失（`COMException`）直接跳过。

## 11. 安全模型

| 项 | 现状 |
| --- | --- |
| 传输加密 | ❌ 明文 TCP / UDP |
| 身份认证 | 8 位数字配对码（对端生成，约 26.6 bit 熵） |
| 暴力破解防护 | 每 IP 每分钟 6 次失败上限 |
| 发现报文 | 明文，含设备 ID 与主机名 |
| 网页桥接 | 每次启动的 48 字符随机令牌 + 同链路校验 |
| 依赖外部服务 | 无 |

**结论**：这是一个可信局域网内的工具。不要在公共 Wi-Fi、访客网络或任何可能被嗅探/中间人的链路上使用。加密链路在路线图上，但目前没有实现。
